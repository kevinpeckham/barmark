# `@barmark/engraver` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish a smaller Verovio 6.4.1 build, made only for what `@barmark/score` asks of it, as the npm package `@barmark/engraver`, proven to draw byte-identical SVG to stock, and let `<barmark-score>` (score 0.4.0) and barmark.dev load it with both files integrity-checked.

**Architecture:** `packages/engraver` holds the pinned build inputs (`build/`), a committed anchor of the build's sizes and digests (`src/info.ts`) and the licence files; the `.wasm` and `.mjs` are compiled by emsdk on the VM, in CI and in the release workflow, never committed, and every build must match `info.ts` byte for byte. A root equivalence gate engraves a fixed corpus with stock `verovio/wasm` and the build, in Node 22, and fails on any byte of difference. `@barmark/score` 0.4.0 gains `verovio-wasm-integrity`: its worker passes Emscripten an `instantiateWasm` hook that downloads and checks the `.wasm` itself, raced against the factory so a failed download never hangs.

**Tech Stack:** Bun 1.3.14 workspace, TypeScript 7 (`tsc`), Biome (tabs), Fallow; emsdk 7.0.0 (emcc, Closure), CMake 4.4.4 (pip, venv); Verovio 6.4.1; GitHub Actions (`actions/cache`, artifacts); Playwright (Chromium); Swamp; SvelteKit (barmark.dev).

**Spec:** `docs/superpowers/specs/2026-11-10-engraver-package-design.md` (approved by Kevin 2026-11-10, all ten questions answered yes). Executors read both.

## Global Constraints

## Review Focus

1. **A `.wasm` served compressed (jsDelivr `Content-Encoding: br`), or as `application/octet-stream`:** the worker fetches the bytes itself, so the MIME type never matters, and the progress bar measures the decoded bytes against the known wasm size, rising to 100%, never against the compressed length. Test: Task 8, "an encoded wasm response is measured against the known wasm size".
2. **A relative `verovio-url`, or one with a query or hash (`/vendor/verovio-module.mjs?v=2`):** the `.wasm` resolves to the sibling `verovio-module.wasm` of the absolute module URL, without the query, and never against the `blob:` URL the glue is imported from. Test: Task 8, "resolves the wasm beside the module URL, never against a blob".
3. **A site that sets `verovio-wasm-integrity` but points `verovio-url` at stock Verovio:** stock ignores the hook, loads normally, and the unused failure promise never becomes an unhandled rejection. Test: Task 8, "a factory that ignores the hook resolves, with no unhandled rejection".
4. **A worker replaced after a crash or a deadline:** the replacement loads the same lite build with the same wasm digest, not stock and not an unchecked wasm. Test: Task 9, "a replacement worker gets the loaded source's wasm digest".
5. **A stale `dist/` left on the VM after a pull that changed `info.ts` or `build/`:** `bun run build` fails, naming the file, both sizes and both digests, and saying to run `bun run compile`; it never packs or serves the stale bytes. Test: Task 3, "a stale dist names the file, both digests and the fix".

## Rulings (where the spec left a choice)

- **`build` versus `compile`.** Root `bun run build` (`bun run --filter '*' build`) runs every workspace's `build`, in every CI `package` row and in `test:browser`, and Bun 1.3.14's `--filter '!name'` does not exclude a package (checked on the VM). So the engraver's `build` script never runs emcc: it emits `dist/info.js`, `dist/info.d.ts`, `dist/index.d.mts` and, when `dist/verovio-module.{mjs,wasm}` are present, checks them against `info.ts`. The emcc build is `bun run compile` (`--update` rewrites `info.ts`). Where the spec says "`bun run build` on the VM" or "`--update`", read `bun run compile`.
- **The banner's release URL is per engraver version,** so a version bump changes the glue's bytes: an engraver release PR runs `bun run compile --update`. The CI dist-cache key therefore hashes `packages/engraver/package.json` as well as `build/**`.
- **`verify-package` packs with `--ignore-scripts`,** so `prepack` is not the guard there: `scripts/smoke-engraver.mjs` checks the packed module's sizes and digests against `info.js`.
- **The lag marker lives in score, not in `info.ts`:** `ENGRAVER_LAGGING` (score `src/verovio.ts`). Marking lag is score's decision at a stock upgrade, and the engraver's published API should not carry it.
- **Score's dev dependency is `"@barmark/engraver": "workspace:*"`,** which packs as the exact version; a plain `"0.1.0"` would make Bun look on npm before 0.1.0 exists.
- **The release workflow's `build-engraver` runs for every tag.** From 0.4.0, score's browser suite (run by `verify` on every release) loads the lite build. `engraver-v*` tags build from clean with no dist cache. Other tags use the dist cache and build on a miss, as CI does.
- **Progress:** `expected` is looked up by the *declared* digest (`verovio-integrity` or `verovio-wasm-integrity`) among the three known builds. With a wasm digest given, the glue's download is reported unmeasured and the `.wasm` measured, so the bar never runs to 100% twice.
- **Version check:** a module loaded from `verovio-url` must report `getVersion()` equal to score's `VEROVIO_VERSION` or starting with `VEROVIO_VERSION + "-"`. A mismatch is a load failure: with `verovio-integrity` set it falls back to the package's own copy with a warning; without it, the load fails (today's rule).
- **The gate runs in Node through a `.mjs` engraver.** `scripts/engraver-equivalence.ts` (run by Bun) builds the corpus's MusicXML and compares. `scripts/engraver-engrave.mjs` (Node 22) engraves with score's built `engraveXml`. Node cannot import the workspace's `.ts` sources.
- **The Q1 `-Oz`/`-Os` rule** is read from the gate's report on CI in Task 5. If the slowest width-375 engraving passes 500 ms before 0.1.0, 0.1.0 itself ships `-Os`, and Kevin is told.
- **Swamp's `equivalence` method** runs for every `pkg` and reports "skipped" for any `pkg` but `engraver`, so the workflow DAG needs no condition.
- **Branches:** Tasks 1–6, 12 and 13 are PR 1 (`feat/engraver`). Tasks 7–11 are PR 2 (`feat/score-engraver`, branched from `feat/engraver`, rebased on `main` after PR 1 merges, merged after 0.1.0 is on npm).
